01 — Project Overview

Pizza Snack Play replaces a single plain-text file that a school used to run its daily snack duty roster — and turns it into a system that can be asked questions.

The source artefact is preserved in the repository and is the whole data model the school was working with: 136 lines, 5 weekly blocks, 21 menu lines, 86 duty assignments, 38 unique student names, covering classes 1–5. Every requirement in this project traces back to a property of that format — not to a survey.

What the source artefact actually contains

Measured from data/output_jadwal_piket.txt — 136 lines total

86 duty assignments 21 menus blank / other
86 duty assignment lines — a name beside a class, with no identity 21 menu lines — free text, Mon–Fri 5 hand-written week headers

1.1  Target Scenarios

Eight recurring events in the school week. Each one is a real moment, not a hypothetical use case.

S1 · every school morning

“What is today’s snack?”

A parent opens a forwarded text file and scrolls to find the date. The app answers in one screen — with the duty guardian’s WhatsApp link beside the menu.

S2 · Sunday evening

Weekly planning

The same file is read twice: once for the menu, once for the duty roster. One view now shows Mon–Fri per class.

S3 · when a class is on duty

Duty rotation

Nobody can tell whose turn it is without reading the whole file. Duty is now a typed relationship, chosen from that class’s roster.

S4 · whenever a date is left open

Filling an unassigned slot

Previously the first reply in a group chat won, untracked. Parents now claim the date themselves, race-safe at the database level.

S5 · once a month

Lock-and-publish cycle

There was no concept of “ready”. A three-state machine now makes a half-announced class structurally impossible.

S6 · monthly coordination meeting

“Is the duty load fair?”

Unanswerable from the file, which records who is on duty but never who took duty. The report ranks every parent and names those who took none.

S7 · when planning next month

Menu reuse & history

Past menus were re-typed by hand. A searchable catalog of 43 menus and 85 menu items is shared across all classes.

S8 · each school year

Parent account lifecycle

Accounts were created one at a time. Now an Excel round-trip: export → edit → import, always through a dry-run preview.

The scenario that shaped the architecture is S4 + S5 together.

Claiming writes back into a schedule row; publishing freezes rows. If both could write freely, a parent could claim a slot in a month the school had already announced. The status machine exists so that is impossible — not merely discouraged.

1.2  Target Users

Four audiences, three of them with real authority. The role model is deliberately small — every extra role is a new way for the school to get its own process wrong.

RoleWho they arePrimary goalAuthorityExplicitly denied
Admin Teacher or staff running the snack programme Keep the whole school’s schedule correct and published Full CRUD on all classes, catalog, categories, holidays, parent accounts, statistics; lock and unlock —
Korlas
class coordinator		 A parent nominated per class Run their own class without waiting for admin Create / edit / delete their class’s schedule while draft; lock and publish their own class; claim open dates (still a parent) ✕ cannot unlock · cannot touch other classes · cannot edit the shared catalog · cannot manage accounts

Cooperative
canteen		 School food provider Know what to prepare Read-only, via Excel export ✕ no login-level write path

Why korlas exists — and why it is powerful inside one class, powerless outside it.

The first version had only admin and parent. In practice one admin could not keep six classes current, and parents could not edit anything. Promoting six parents to admin would have given each of them the power to rewrite the whole school’s catalog and every other class. So a third role was introduced with a hard boundary — enforced by requireRole() in the API, and merely reflected by <RoleGate> in the UI.

1.3  Value Proposition

Turns a document that could only be read into a system that can be asked questions — without adding an administrator.

pillar 01

Answer, not archive

Answers the three questions people actually ask: today’s snack, my child’s duty turn, has my class been published.

pillar 02

Authority at the edge

Moves the monthly workload from one admin to six coordinators while keeping the school-wide catalog under single ownership.

pillar 03

Fairness becomes measurable

Because claims are stored separately, the system can name the parents who took no duty — a question the source document could not answer at all.

pillar 04

Zero marginal cost

Workers + D1 on the free tier. No server, no licence, no app store. A snack programme has no budget line for software.

1.4  Real-World Scenario Insights

1.4.1  Where the pain points came from

The pain points were not gathered from a survey. They were extracted from the artefact the school actually used:

Pain pointRoot cause visible in the source format
No searchMenu names are free text inside day lines — “when was jeruk served?” means reading all 21 lines
No notificationThe file is a snapshot; nothing tells anyone it changed
Hard to edit safelyWeek headers are written by hand and were already wrong — one block was labelled 14 - 18 Oktober 2026 (Mon–Fri) although 14 October 2026 is a Wednesday
No historyThe file is overwritten month to month; only two months survive in the repository
No reusable catalogNothing links “Puding Roti” in September to “Puding Roti” in October
No duty trackingDuty is a name beside a class, with no identity — no parent record is referenced anywhere

Two of these are data-integrity defects, not convenience problems:

  • The mis-labelled week header is a real error found in the school’s own document. The importer now matches each day label against the real calendar, shifts a mis-labelled week to the correct Mon–Fri, and warns the user. A manual spreadsheet cannot do this.
  • Duty names had no identity. The fix was to make the duty officer a relationship (petugas_student_id + petugas_parent_id), with the printed name kept only as a denormalised display copy. The API refuses duty names supplied by the client and resolves them against the class roster server-side.

1.4.2  Target audience and the core problem solved

The snack schedule is a shared obligation — every family takes a turn — but it is recorded in a private document that no family can query, and that only one person can safely edit.

The read half

Parents had no reliable way to know their turn. Closing it means authentication — each family sees only its own child’s class — and a per-class data model.

The write half

One admin could not maintain six classes. Closing it means a delegated role with a hard boundary, plus a lock/publish gate so “announced” and “still being edited” can never be confused.

Who it is not for

No student accounts — duty is a family obligation and the guardian holds the phone. No attendance, grades or messaging. Every feature must trace back to the snack roster.

Why the obvious fix fails. “Put the file in a shared spreadsheet” solves the read half for people who already know the sheet exists, and makes the write half worse: a shared sheet has no notion of who may edit which class, no published state, and no way to answer “who has never taken a turn” — because the sheet records duty, not claims. The claim table only exists because the system is an application.

02 — Comprehensive Solution Design

A three-state schedule machine, a two-layer authority model, and a nine-domain API — each chosen to make a specific failure impossible rather than merely unlikely.

2.1  Business Architecture

Authority is enforced twice, and the two layers do different jobs

LayerMechanismPurpose
API — authorityrequireRole() on every write routeThe actual boundary. Returns 403 regardless of what the client sends.
API — data scopeclassScope · canWriteClass(user, row.className)On PUT/DELETE the class is read from the database row, never from client input — so a korlas cannot hijack another class by changing a parameter.
UI<RoleGate need="admin" | "schedule" | "catalog">Hides controls the user cannot use. Documented explicitly as cosmetic — it avoids offering impossible actions; it enforces nothing.

The schedule lifecycle

The rule that matters most

POST /schedules/publish refuses with 409 drafts_remaining when any row is still draft — and names the offending classes. This is what makes a half-published class structurally impossible.

The one deliberate exception

On a locked or published row, the duty officer alone may be set — duty is often filled after announcement. A mixed patch (duty plus menu, notes or holiday) is still rejected with 409 not_editable.

Two bulk-action semantics, kept deliberately different

Range / class basedSelected-rows based
EndpointsPOST /schedules/lock · /schedules/publishPOST /schedules/bulk/{lock,publish,unlock}
Mismatched status409 drafts_remaining — the whole request is refusedCounted as skipped, returns 200
Class scopeResolved from the request via resolveBulkClassesTaken from each row — never from the client

The asymmetry is intentional. A month-level operation that silently skipped a class would produce exactly the half-published state the status machine exists to prevent, so it fails loudly. A hand-ticked set of rows is an explicit choice, so the correct behaviour is to act on the qualifying rows and report the rest.

The claim mechanism — first come, first served

Race safety

UNIQUE(schedule_id) on schedule_claims — the database, not the application, decides the winner.

One source of truth

A successful claim writes back into schedules.petugas_*, so a claim can never disagree with the schedule.

Per class

The same date in two classes is two rows — class 1 claiming does not block class 2.

Fairness reporting

Because claims are their own table, the report can rank parents by duties taken and name those who took none.

Two schema decisions were reversals, and reversals are the most reliable evidence that a design was tested against reality:

No composite foreign key on the duty officer

A composite FK needs an exactly matching unique index, which forces a table rebuild. A rebuild needs PRAGMA foreign_keys=OFF — and that pragma is a silent no-op inside a transaction, while wrangler d1 migrations apply wraps migrations in one. The migration passed locally, failed in production with FOREIGN KEY constraint failed, and the “successful” path left 292 foreign_key_check violations. Migration 0007 is now a plain ALTER TABLE ADD COLUMN; consistency is enforced in the service layer.

Category images live in the database

Stored as base64 data URIs and validated on both client and server. The catalog DTO was split in two — CategorySummaryDto (no image; used by menus and schedules) and CategoryDto (with image; only on the category page) — so a month of schedules containing dozens of menus does not duplicate image payloads that nothing displays.

2.3  How Prompts Drive the AI Generation

This project was generated by prompt over 113 commits in 31 days. The mechanism is not “ask an AI for an app” — it is a specification-first loop in which the prompt is the specification, the repository is the record, and a verifier is named before any code is written.

01Domain truth A human supplies what the AI cannot know: the school’s real schedule, roles, and authority boundaries.
→
02Prompt Carries five slots: intent · constraint · evidence · acceptance · artefacts.
→
03AI generates Migration · API · UI · documentation · and the test that will judge it.
→
04Verifier runs tsc · eslint · vite build · the named test suite.
→
05Commit & record Code, PRD changelog entry, and project memory committed together.
↺ On failure: the prompt is corrected and re-run — and the constraint is written into persistent memory so the same mistake cannot recur in a later session.

Prompt anatomy used in this project

Every substantive prompt carries five slots. The pattern is visible in the PRD changelog, where each version records the same five things.

SlotQuestion it answersExample from this project
1 · IntentWhat changes for the user?“Admin must be able to publish all six classes in one action”
2 · ConstraintWhat must not break, and what is forbidden?“Korlas may lock their own class, not others. Do not add a class table.”
3 · EvidenceWhat in the existing code decides the design?“Check resolveBulkClasses before choosing where class scope is resolved.”
4 · AcceptanceHow will we know it worked?“409 drafts_remaining names the offending class; test-api.mjs section 23 covers it.”
5 · ArtefactsWhat else must be updated?“PRD, README, UAT_Result, test-api.mjs.”

Slot 4 is what makes the loop converge. A prompt that does not name its verifier produces code that passes nothing in particular; a prompt that names 409 drafts_remaining produces a test that will still be running a year later.

Prompt intentGenerated artefactVerifier named in the prompt

Note the sixth row: a prompt was refused by its own constraint.

The refusal is recorded in the PRD as a correction (v1.10). That is the loop working as intended — the constraint slot exists precisely so that a plausible-sounding request can be rejected before it corrupts production data.

Guardrails carried inside the prompts

Hard-won constraints are written into the project’s persistent memory and re-stated in prompts, so a later session cannot silently undo them.

Never trust a duty name from the client

Duty is a relationship, not a string — a client-supplied name would let a typo create a new “student”.

Never rebuild a table in a D1 migration

PRAGMA foreign_keys=OFF is a no-op inside a transaction, and d1 migrations apply uses one.

Never let 409 become skipped

Silent skipping is how a class gets published half-done.

Never let the UI be the only enforcement

<RoleGate> hides; requireRole() enforces.

Always build before deploy

wrangler deploy uploads dist/ as-is — it does not compile.

Never trust piped wrangler output

Truncated output has produced wrong conclusions; write to a file and parse the whole JSON.

Why the generation is auditable

PRD changelog v1.1 → v1.21

Every entry records the prompt’s intent, the design decision, and any correction to an earlier claim. Several entries explicitly retract earlier statements, so the document shows its own errors.

3.4  Honest Limits

Stated deliberately: a description that claims no gaps is not a description of a real system.

  • PDF export is not built. Excel export is (schedules and accounts); the print-oriented PDF is still open (F5 partial).
  • No push notifications. F6 remains planned; today the app must be opened to be read.
  • No student-facing accounts. Duty is modelled as a family obligation, so the guardian’s account is the only entry point. A student view would be a new decision, not a setting.
  • No offline data. The app is installable as a PWA, but schedules are not cached for offline reading — a deliberate choice, since a stale schedule is worse than no schedule.
  • No usage analytics. Nothing tracks which pages parents actually open, so the adoption claims in §3.3 are measurable but not yet measured.
  • import_logs is written, not surfaced. The audit trail exists; the UI for it does not.
  • Single-school assumption. The data model has no school_id. Multi-tenancy would be a migration, not a configuration change.
